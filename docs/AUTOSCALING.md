# Автомасштабування

## Налаштування (Terraform, `infra/app.tf`)
| Параметр | Значення |
|---|---|
| Мінімум екземплярів | 1 |
| Максимум екземплярів | 4 |
| Метрика | CPU (utilization) |
| Цільове значення | 60% |
| Ресурси одного екземпляра | 0,25 vCPU, 0,5 ГБ |

## Чому саме так
- **Мінімум 1.** Сервіс завжди готовий відповісти. При мінімумі 0 перший запит
  чекав би запуску контейнера (холодний старт), а один екземпляр коштує мало.
- **Максимум 4.** Це обмеження лабораторної та бюджету. У нашому тесті на 40
  користувачів вистачало двох екземплярів, тож чотири це запас.
- **Ціль CPU 60%.** Новий екземпляр стартує не миттєво (приблизно хвилину),
  тому потрібен запас: при 60% у екземпляра лишається 40% вільного CPU, щоб
  пережити стрибок навантаження, поки додається новий. Якби ціль була 90%,
  сервіс уже сповільнювався б до появи нового екземпляра. Якби 30%, ми
  платили б за зайві екземпляри.
- Метрика CPU підходить, бо наш застосунок реально навантажує процесор
  (обробка запитів, робота з базою), і вона вимірюється самою платформою
  без жодних додаткових налаштувань.

## Cooldown (час очікування перед зменшенням)
Azure перевіряє метрику приблизно раз на 30 секунд. Збільшення кількості
екземплярів відбувається одразу, коли метрика перевищила ціль. Зменшення
відбувається обережніше: платформа чекає приблизно 5 хвилин (значення за
замовчуванням, ми його не змінювали), чи навантаження не повернеться.
Ми це спостерігали: тест закінчився о 00:44:30, CPU впав до нуля близько
00:46, а другий екземпляр зник лише о 00:50.

**Що було б при cooldown = 0.** Платформа прибирала б екземпляр одразу, щойно
CPU на мить опускається нижче цілі. Навантаження зазвичай коливається, тому
система постійно додавала б і прибирала екземпляри («гойдалка», flapping).
Кожен запуск нового екземпляра це 30-60 с, під час яких він не обробляє запити,
а прибирання екземпляра обриває запити, що в ньому виконуються. У результаті
було б більше помилок і непотрібних витрат. Тому довге очікування перед
зменшенням це свідомий компроміс: трохи дорожче, але стабільніше.

## Дашборд (Terraform, `infra/monitoring.tf`)
Дашборд `cloudlab-dashboard` має п'ять графіків: екземпляри, CPU, запити за
хвилину, затримка та помилки 5xx. Примітка: Azure не дає метрики «бажана
кількість екземплярів», тому показуємо фактичну; метрика затримки від платформи
не працює, p95 береться з логів застосунку (див. `docs/CACHE.md`).

### Хронологія тесту (00:35 - початок, час наш)
| Час | Подія |
|---|---|
| 00:35 | Початок тесту, один екземпляр |
| 00:37 | CPU росте: 109 млн нано-ядер (44% від ліміту) |
| 00:38 | CPU 165 млн (66%): **перетнуто поріг 60%** |
| 00:39 | **З'явився другий екземпляр**, CPU падає до ~50% |
| 00:42 | Спрацював алерт (лист про CPU) |

| 00:46 | CPU впав майже до нуля |
| 00:49 | Лист про відновлення |

## Пояснення затримок
**Чому між перетином порога і новим екземпляром минає час.** Поріг було
перевищено о 00:38, а другий екземпляр з'явився о 00:39, тобто приблизно через
хвилину. Ця хвилина складається з кількох кроків: метрика CPU збирається раз на
хвилину і усереднюється; Azure опитує її раз на ~30 секунд; потім потрібно
завантажити образ з реєстру, запустити контейнер, підключитись до бази і
пройти перевірку готовності. Весь цей час перший екземпляр працює під повним
навантаженням (в нашому тесті CPU досягав 66%), тому при різкому стрибку
навантаження затримка на кілька десятків секунд неминуча.

**Чому зменшення таке повільне.** Другий екземпляр зник через ~5,5 хвилин після
кінця тесту і через ~4 хвилини після того, як CPU впав до нуля. Це навмисна
затримка (cooldown), описана вище: платформа перевіряє, що навантаження
справді зникло, а не лише на мить стало меншим. Платимо за це кількома
хвилинами зайвого екземпляра, але уникаємо гойдалки.
